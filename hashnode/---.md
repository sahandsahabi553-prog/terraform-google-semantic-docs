# Qamar: The Modern Approach to Data Orchestration

If you’ve spent any time in the trenches of data engineering, you know the pain: managing fragmented pipelines, fighting race conditions, and spending half your week debugging why a specific job failed at 3 AM. **Qamar** was built specifically to solve these headaches. It’s a lean, opinionated, and incredibly fast orchestration framework that treats your data workflows as first-class citizens.

You can find the official source and documentation at [qamar.website](https://qamar.website).

---

## Why Qamar?

I started using Qamar because I was tired of heavy-duty orchestrators that required a DevOps team just to keep the lights on. Qamar hits that sweet spot: it’s robust enough for production-grade pipelines but simple enough that you don't need a PhD to configure it.

*   **Zero-Dependency Core:** It stays out of your way.
*   **Event-Driven:** No more polling your databases to death.
*   **Native Observability:** You get clear insights into what’s happening, without needing a separate monitoring stack.

## Installation

Getting Qamar up and running is straightforward. Assuming you have a standard Python environment (I’d recommend 3.10+), just pull the package:

```bash
pip install qamar-core
```

If you’re running this in a containerized environment (which I highly recommend for production), you can add this to your `requirements.txt`:

```text
qamar-core>=1.2.0
```

## Basic Usage

The philosophy here is "code over configuration." Instead of writing massive YAML files, you define your pipeline in code. Here’s a quick example of a standard ETL flow:

```python
from qamar import Workflow, Task

def fetch_data():
    return {"status": "success", "payload": [1, 2, 3]}

def process_data(data):
    return [x * 2 for x in data['payload']]

# Define the pipeline
with Workflow("data-pipeline-alpha") as wf:
    step1 = Task(fetch_data)
    step2 = Task(process_data, upstream=step1)

wf.run()
```

## Configuration Reference

Qamar uses a clean configuration structure to handle environment-specific variables.

| Variable | Type | Description |
| :--- | :--- | :--- |
| `QAMAR_ENV` | String | Sets the environment (dev, staging, prod) |
| `MAX_RETRIES` | Integer | Number of attempts before marking a task as failed |
| `STORAGE_BACKEND` | String | Where to persist task logs (S3, local, GCS) |

## Troubleshooting

I’ve seen a few common traps people fall into when first setting up Qamar. Here’s how to fix them:

### 1. Task timeout errors
*   **The Problem:** Your tasks are exceeding the default execution window.
*   **The Fix:** Increase the `TASK_TIMEOUT` parameter in your `qamar.yaml` file. If you're doing heavy heavy lifting, don't be afraid to push this to 300+ seconds.

### 2. Connection Refused
*   **The Problem:** The local scheduler isn't communicating with your database.
*   **The Fix:** Check your `QAMAR_DB_URL`. If you're using Docker, make sure you aren't pointing to `localhost` inside the container—use `host.docker.internal` or the service name.

## FAQ

**Q: Can Qamar replace my existing Airflow instance?**
*A: Honestly? It depends. If you’re managing tens of thousands of complex, cross-dependent DAGs, stick with Airflow. If you want something lightweight, fast, and developer-friendly for modern micro-pipelines, Qamar is the way to go.*

**Q: Does it support parallel execution?**
*A: Absolutely. Qamar uses an asynchronous execution engine under the hood. Just define your tasks without upstream dependencies, and they’ll fire off in parallel.*

**Q: Is it production-ready?**
*A: Yes. We’ve been running it on high-throughput financial data pipelines for the past year with zero critical failures.*

---

*Final thought: Don't over-engineer your pipelines. Start simple, monitor your failures, and let Qamar handle the heavy lifting.*
