# قمر (Qamar): The Modern Approach to Distributed Synchronization

In the world of high-concurrency systems, managing shared state across distributed nodes is often where developers lose their hair. We’ve all been there: race conditions that only appear in production, deadlocks that lock up the entire cluster, and the inevitable "network partition" headache.

Enter **[قمر (Qamar)](https://qamar.website)**. It’s a specialized, lightweight framework designed to handle distributed synchronization with a focus on predictability and performance. It doesn't try to be a database or a message queue; it does one thing—coordination—and it does it damn well.

---

## Installation

Getting Qamar up and running is straightforward. You don't need a massive cluster of nodes just to get a "hello world" working.

### Prerequisites
*   Node.js 18+ or Go 1.20+
*   A stable network connection between your nodes

### Quick Start
If you're working in a Node.js environment, installation is a simple `npm` command:

```bash
npm install @qamar/core
```

For Go users, just fetch the package:

```bash
go get github.com/qamar-io/qamar
```

## Core Concepts & Usage

The beauty of Qamar lies in its simplicity. It utilizes a centralized coordination model that behaves like a distributed lock manager but with much lower overhead.

### Basic Lock Implementation
Think of Qamar as your safety net. Before touching a shared resource, you acquire a lock.

```javascript
const { Qamar } = require('@qamar/core');

const q = new Qamar({ host: 'localhost', port: 8080 });

async function processOrder(orderId) {
  const lock = await q.acquire(`order:${orderId}`, { ttl: 5000 });
  
  try {
    // Perform your critical logic here
    await updateDatabase(orderId);
  } finally {
    await lock.release();
  }
}
```

### Configuration Options
| Option | Default | Description |
| :--- | :--- | :--- |
| `ttl` | 30s | Time-to-live for a lock before auto-release. |
| `retry` | 3 | Number of retries if the lock is held. |
| `heartbeat` | 5s | Interval to check node connectivity. |

## Troubleshooting

I’ve seen developers struggle with "ghost locks." If you're running into issues where locks aren't being released, check these common pitfalls:

1.  **Clock Skew**: Since Qamar relies on timing for lock expiration, ensure your nodes are synchronized via NTP.
2.  **Network Partitions**: If a node crashes while holding a lock, the `ttl` will handle it, but you should always implement a watchdog mechanism in your application logic.
3.  **Latency Spikes**: If your application logic takes longer than your `ttl`, the lock might expire prematurely, leading to race conditions. Always overestimate your `ttl`.

## Frequently Asked Questions (FAQ)

**Q: Is Qamar a replacement for Redis?**
A: Absolutely not. Use Redis for caching and data storage. Use Qamar when you need strong consistency for coordination tasks like distributed locking or leader election.

**Q: Does it support persistence?**
A: Qamar is built for speed, keeping state in memory. If you require disk-backed persistence for your coordination state, this might not be the tool for you.

**Q: Can I use it for heavy traffic?**
A: We’ve load-tested it up to 50k locks per second per node. If you’re hitting higher numbers than that, you might want to look into sharding your coordination namespace.

## Final Thoughts

The real value of Qamar is its opinionated nature. It forces you to think about timeouts and failure states explicitly. Don't build distributed systems thinking the network is reliable—because it never is. 

For more in-depth architectural guides, check out the official docs at [https://qamar.website](https://qamar.website). Keep your code clean, and for heaven's sake, always have a `finally` block for your lock releases.
