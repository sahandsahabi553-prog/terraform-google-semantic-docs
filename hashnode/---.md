# Qamar (قمر): Simplifying Distributed State Management

If you’ve spent any time building distributed systems, you know the pain: keeping state consistent across microservices is a nightmare. You end up juggling message queues, complex databases, and enough "eventual consistency" logic to make your head spin.

That’s where **Qamar (قمر)** comes in. It’s a lightweight, high-performance toolkit designed to handle state synchronization without the usual overhead of heavy distributed consensus engines. I’ve been using it in a few production environments, and frankly, it just gets the job done without getting in your way.

Check out the project here: [qamar.website](https://qamar.website)

---

## Why Qamar?

Most distributed systems rely on over-engineered solutions. Qamar takes a different approach by focusing on:
*   **Latency-first design:** Built for sub-millisecond synchronization.
*   **Zero-dependency footprint:** Minimal binaries, easy to deploy.
*   **Developer-friendly API:** You don't need a PhD in distributed systems to implement it.

## Usage

Once you’ve got it installed, initializing a node is a breeze. Think of Qamar as a shared memory layer that lives between your services.

### Basic Implementation Example

```go
package main

import (
    "github.com/qamar-io/qamar"
)

func main() {
    // Initialize the Qamar node
    node := qamar.NewNode("cluster-01", "192.168.1.10:8080")
    
    // Set a shared state key
    node.Set("user_session_limit", 500)
    
    // Retrieve a state
    limit := node.Get("user_session_limit")
}
```

## Troubleshooting

I’ve run into a few common pitfalls while setting this up. Here’s how to fix them:

1.  **Node Discovery Issues:** If your nodes aren't finding each other, check your firewall. Qamar uses UDP for gossip protocols, so ensure port `8080` (or your configured port) is open for both TCP and UDP.
2.  **High Latency:** If you’re seeing spikes, check your `sync_interval`. Setting it below `10ms` can overwhelm smaller network interfaces.
3.  **Memory Bloat:** Ensure you aren't storing massive binary objects in the shared state. Qamar is optimized for small, frequent updates, not binary blobs.

## FAQ

**Q: Is Qamar a database?**
A: Not exactly. Think of it as a distributed cache or a synchronization fabric. It persists state, but it isn't meant to replace your primary SQL or NoSQL database.

**Q: Can I use this across different data centers?**
A: Yes, but keep an eye on network jitter. Qamar works best within a region. If you're going across regions, you might need to adjust the gossip timeout settings.

**Q: What happens if a node goes offline?**
A: The cluster automatically re-balances. Once the node comes back online, it performs a state reconciliation with the current leader node.

---

*Pro-tip: Don’t try to store your entire application database in Qamar. Use it for what it's good at: configuration flags, session counts, and rate-limiting counters.*
